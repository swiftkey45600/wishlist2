# Backend

FastAPI-сервер для Wishlist Service.

> Чтобы поднять весь проект одной командой (backend + frontend), используйте скрипт из корня:
> `.\run.ps1` на Windows или `./run.sh` на Linux/macOS — см. [корневой README](../README.md).
> Ниже — запуск только backend.

## Требования

- Python 3.10+ (в коде используется синтаксис `timedelta | None`)

## Установка и запуск

Все команды выполняются **из корня проекта**, а не из папки `app`.

```bash
# Создать виртуальное окружение
python -m venv .venv

# Активировать виртуальное окружение
source .venv/bin/activate      # macOS / Linux
.venv\Scripts\activate         # Windows

# Установить зависимости
pip install -r requirements.txt

# Создать .env с ключом подписи JWT — без него сервер не стартует
python -c "import secrets; print('JWT_SECRET_KEY=' + secrets.token_urlsafe(48))" > .env

# Запустить сервер
uvicorn app.main:app --reload
```

Либо то же самое одной командой: `./run.sh --backend-only` (`.\run.ps1 -BackendOnly` на Windows).

## Переменные окружения

| Переменная | Обязательна | Описание |
|---|---|---|
| `JWT_SECRET_KEY` | да | ключ подписи JWT. Пустое значение — `RuntimeError` при импорте приложения |

Файл `.env` лежит в корне проекта, шаблон — `.env.example`.

## База данных

SQLite, файл `wishlist.db` в корне проекта. Отдельная установка не нужна: при старте
`init_db()` применяет `app/schema.sql` и досоздаёт недостающие колонки. Чтобы начать с чистой
БД, достаточно удалить `wishlist.db` и перезапустить сервер.

## Совместный сбор

`contribution_goal` задаёт цель сбора при создании или редактировании подарка.
`contribution_total` рассчитывается сервером. При достижении цели создаётся бронь;
при отмене взноса и уменьшении суммы ниже цели бронь сбора снимается.

- `GET`, `POST /events/public/{token}/gifts/{gift_id}/contributions` — список и создание взносов;
- `DELETE /events/public/{token}/gifts/{gift_id}/contributions/{id}` — отмена взноса;
- `GET /gifts/{gift_id}/contributions` — список для владельца с JWT.

Взнос содержит `amount`. Для гостя обязательны `name` и `secret_word`; слово хранится
как bcrypt-хеш. Для вошедшего пользователя используется имя из аккаунта, отмена доступна автору.
Гостевая отмена требует того же слова и ограничена по числу попыток.

## Архив и копирование событий (S8.2)

События имеют `status=active|archived`. Владелец может архивировать и восстанавливать
событие, а также создавать независимую копию с подарками и тегами, без броней и взносов.
В архиве новые брони и взносы запрещены, существующие можно отменять по прежним правилам.

Контракт API, правила миграции и примеры для frontend:
[S8.2 — архив и копирование](../docs/S8_2_EVENT_LIFECYCLE.md).

## Почта и восстановление пароля (S9.2)

Email можно указать при регистрации, в профиле или через `POST /users/me/email`.
Подтверждение и сброс используют SMTP и одноразовые ссылки с хранением хешей в БД.
После смены пароля старые JWT отзываются; запросы писем ограничиваются общими счётчиками SQLite.

- [Подтверждение email](../docs/S9_2_EMAIL_VERIFICATION.md).
- [Сброс пароля, ограничения и отзыв сессий](../docs/S9_2_PASSWORD_RESET.md).
## Доступ и обновление данных

- `POST /reservations/` требует JWT и `public_token` события в теле запроса.
- Чтение тегов по ID события и профиля по ID доступно только владельцу.
  Гости получают теги подарков через `GET /events/public/{token}`.
- `cover_image_id` сохраняется при создании и редактировании события; удаление изображения
  очищает ссылку на обложку.
- JWT привязан к текущим учётным данным аккаунта. Смена пароля отзывает старые токены;
  `PATCH /users/me` возвращает новый `access_token`, который фронтенд сохраняет.
  Токены прежнего формата требуют повторного входа после обновления.
- Публичная отправка вопросов ограничена десятью запросами в минуту с одного IP.

### Напоминания о событиях

Пользователь с подтверждённой почтой может включить напоминания в профиле. За неделю и за день до начала события по одному письму получат владелец и зарегистрированные гости с бронью, если они включили настройку. Анонимным гостям письмо не отправляется: их адрес не хранится. Письма не раскрывают брони владельцу.

Для автоматической отправки настройте SMTP и установите `EVENT_REMINDERS_ENABLED=true` в окружении сервера, затем перезапустите приложение. Фоновая проверка выполняется раз в час по местной дате сервера; сохранённый ключ предотвращает повторную отправку между процессами. Если процесс прервётся во время отправки, повтор не гарантирован. Успешный ответ SMTP подтверждает приём письма сервером, а не доставку во входящие.


### Конфиденциальность

Пароли аккаунтов и секретные слова гостей хранятся как bcrypt-хеши с отдельной солью. Они не возвращаются API; значения запросов исключены из ошибок валидации. Личные API-ответы не должны кэшироваться. Приложение не ведёт журнал тел запросов.

Подарки и события доступны владельцу; публичная ссылка предоставляет доступ только к явно выбранным данным. Владелец может отозвать ссылку списка подарков. Ссылка является ключом доступа: любой её получатель может открыть опубликованный список. Старые ссылки-снимки требуют повторного создания для бронирования. Отзыв ссылки не удаляет уже сделанные брони.

Фотографии нельзя получить, угадав числовой ID: требуется разрешение владельца или подписанный URL конкретного изображения. Такой URL разрешает просмотр только фотографии и перестаёт работать после удаления файла/записи или смены JWT-ключа. Прикреплять фото другого пользователя по номеру запрещено. Идентичные повторные загрузки получают отдельное разрешение.

Это контроль доступа на сервере, а не сквозное шифрование: администратор с доступом к рабочей базе и серверу технически может читать названия, описания, события и фотографии. Для защиты от самого оператора требуется отдельная архитектура с шифрованием в браузере и ключами у пользователей. Права на рабочую базу и резервные копии следует выдавать только ответственным за эксплуатацию; не копировать пользовательские данные в тестовые окружения.


### Длительность событий и карта

В запросах создания, редактирования и копирования события `duration_days` (1–3650) задаёт число календарных дней, включая день начала. Сервер рассчитывает внутреннюю `end_date`; поле оставлено для совместимости со старыми данными. Автоархив выполняется со следующего дня после последнего дня события. Длительность больше одного дня требует даты начала.

Карта передаёт сервису тайлов только origin сайта через `strict-origin-when-cross-origin`, не раскрывая путь к событию или токен ссылки. Общая политика `no-referrer` для остальных ресурсов сохранена. При необходимости адрес совместимого сервиса тайлов задаётся через `VITE_MAP_TILE_URL` при сборке; при смене провайдера нужно также проверить требования к атрибуции.
